# BabySteps · 成长星球 Stitch UI PRD

**版本：** 1.0

**日期：** 2026-08-03

**用途：** 交给 Google Stitch 生成桌面端与移动端 UI；生成结果由现有 React + wagmi 项目接入

**当前阶段：** 只进行产品与界面设计，不实施功能代码

**目标网络：** Ethereum Sepolia 测试网

## 1. 一句话产品定义

BabySteps · 成长星球是一款面向宝爸宝妈、爷爷奶奶等成年照护者的 Web3 课程概念验证产品。用户使用专用 Sepolia 测试钱包记录日常陪伴活动，获得无价格、不可兑换但可在测试钱包间赠送的“成长星”，推动原创虚拟伙伴“星宝”成长。

它不是儿童档案、健康工具、育儿建议、代币投资产品或 NFT 项目。

## 2. 设计任务

请为同一个响应式单页 DApp 生成：

1. 1440 px 桌面端主界面；
2. 390 px 移动端主界面；
3. 关键状态变体，包括钱包未连接、错误网络、活动可领取、活动冷却、当天达上限、等待签名、链上确认、交易成功、交易失败、表单校验失败和清空便签二次确认；
4. 可复用组件、颜色/字号/间距 token；
5. 可导出到前端或 Figma 的设计稿。

Stitch 只负责界面与交互状态表现，不生成或替代智能合约、钱包连接、链上查询、交易提交、交易确认或业务随机逻辑。

## 3. 产品目标

### 3.1 用户目标

- 不需要理解区块链术语，也能看懂“连接测试钱包 → 记录陪伴 → 等待确认 → 星宝成长”的流程。
- 每次可执行操作都清楚、安全，反馈温和，不制造金融收益感。
- 字体、按钮和信息层级适合中老年照护者使用。
- 用户能区分“累计养成值”和“可赠送成长星”。
- 用户能看出公开链上便签是课程基础作业，且与 BabySteps 养成功能相互独立。

### 3.2 课程验收目标

页面必须清楚保留并展示以下能力：

- Vite + React 前端；
- wagmi 连接 MetaMask；
- Sepolia 网络识别与切换；
- 从合约读取真实状态；
- 发起活动、赠送积分、保存便签和清空便签交易；
- 等待 transaction receipt 成功后刷新状态；
- 提供 Sepolia Etherscan 交易链接；
- 公开链上便签的读取、覆盖、刷新恢复和清空。

## 4. 非目标

本次设计不得加入：

- 主网、真实货币、价格、收益率、挖矿、空投、质押、兑换或提现；
- ERC-20 交易界面、NFT 市场、钱包资产组合或 K 线；
- 儿童姓名、照片、生日、学校、位置、健康、疫苗、喂养量或作息数据输入；
- 根据真实孩子生成头像；
- 登录注册、后端数据库、排行榜、社交动态或聊天；
- 购买、商城、抽奖、博彩或付费功能；
- 真实婴儿需求判断或育儿提醒。

## 5. 目标用户

| 用户 | 主要需求 | 设计响应 |
|---|---|---|
| 宝爸宝妈 | 快速记录日常陪伴，看到轻量反馈 | 三张清晰活动卡、少文字、强状态反馈 |
| 爷爷奶奶 | 不熟悉钱包和 Web3，也能逐步操作 | 大字号、大按钮、明确步骤、避免术语 |
| 课程老师 | 快速识别作业要求和链上证据 | 独立课程实验区、交易链接、Sepolia 标识 |

## 6. 核心产品规则

### 6.1 双账本成长星

页面必须同时展示两个概念，不能合并：

- **累计养成值：** 只因当前钱包自己记录活动而增加，决定星宝阶段；赠送不会减少，收到别人的成长星也不会增加。
- **可赠送成长星：** 当前可以转给其他 Sepolia 测试钱包的余额；活动会增加余额，赠送会减少，收到赠送会增加。

辅助文案：

> 收到的成长星不会增加星宝阶段；赠送也不会让星宝退化。

### 6.2 星宝阶段

“星宝”是原创通用虚拟伙伴，不代表孩子本人、发育、能力或表现等级。

| 累计养成值 | 阶段 | 视觉表现 |
|---:|---|---|
| 0–2 | 星蛋 Egg | 温暖发光的星蛋，轻微呼吸感 |
| 3–7 | 星芽 Sprout | 星蛋长出嫩芽或小触角 |
| 8–14 | 探索星宝 Explorer | 小星宝带探索包或小围巾 |
| ≥15 | 闪耀星宝 Star | 星宝进入温暖阅读角，带故事帽 |

首轮进度按 `min(累计养成值, 15) / 15` 显示，最高 100%。达到 15 后显示“首轮养成已完成”，真实累计值仍继续增长，但本版不承诺第二轮形态。

### 6.3 活动与随机游戏状态

| 活动 | 单次奖励 | 链上随机冷却 | UTC+8 每日上限 | 冷却文案 |
|---|---:|---:|---:|---|
| 喂养陪伴 | +3 | 3–4 小时 | 6 次 | 星宝现在还不饿 |
| 户外陪伴 | +5 | 8–12 小时 | 2 次 | 星宝正在休息 |
| 亲子共读 | +7 | 4–6 小时 | 3 次 | 星宝还在回味故事 |

页面必须持续显示：

> 这是随机游戏状态，不代表真实婴儿的饥饿、睡眠或活动需求。

重要交互规则：

- 活动可领取时才显示主按钮“记录这次陪伴”。
- 冷却中不显示按钮，只显示对应拟人文案。
- 达到当天上限时不显示按钮，显示“星宝今天已经很充实了”。
- 读取失败或状态未知时不显示领取按钮，显示重试入口。
- 页面不得显示下次可领取时刻、倒计时、剩余小时或分钟。
- 不得在隐藏文本或 `aria-label` 中偷偷加入具体冷却时间。
- 交易等待签名或确认期间，已触发的按钮可以保留但必须禁用，防止重复交易。

## 7. 信息架构

页面为单页纵向故事流，固定顺序如下：

1. 品牌 Hero 与 Sepolia 概念验证提示；
2. 三项使用前须知；
3. 步骤 1：连接测试钱包；
4. 步骤 2：星宝与活动养成；
5. 步骤 3：测试钱包间赠送成长星；
6. 步骤 4：公开链上便签（课程实验）；
7. “这份作业展示了什么”课程证据区。

不要使用多层导航、侧栏后台、交易仪表盘或复杂 tab。移动端保持相同阅读顺序。

## 8. 页面详细需求

### 8.1 Hero

必须包含：

- 产品名：`BabySteps · 成长星球`
- 标签：`课程概念验证 · Sepolia 测试网`
- 主文案：`记录一件小小的陪伴，让原创虚拟伙伴“星宝”在测试链上慢慢长大。`
- 价值提示：`成长星无价格，只用于 Sepolia 课程演示；可在测试钱包间赠送，不可兑换。`
- 原创星宝主视觉或成长轨迹，不要使用币价、K 线、金币雨、火箭、钻石手或金融图标。

### 8.2 使用前须知

使用三张简洁卡片：

1. **公链长期公开**：钱包、活动、交易时间和积分变化可被长期查看，请只用专用测试钱包。
2. **只记录活动类别**：这是成年照护者自报选择，不能证明现实活动真实发生或育儿质量。
3. **不采集儿童资料**：不要填写或上传儿童姓名、照片、生日、学校、位置、健康或疫苗信息。

### 8.3 钱包卡片

卡片标题：`步骤 1 · 连接测试钱包`

状态与操作：

| 状态 | 展示 | 操作 |
|---|---|---|
| 未安装 MetaMask | 简短安装说明 | `安装 MetaMask` 外链 |
| 未连接 | “尚未连接测试钱包” | `连接 MetaMask` |
| 正在连接 | 明确进度 | 禁用重复连接 |
| 错误网络 | 显示当前网络与 Sepolia 要求 | `切换到 Sepolia` |
| 已连接 | 缩略地址、Sepolia 徽章 | `断开连接` |
| 读取失败 | 友好错误，不显示原始堆栈 | `重试读取` |

按钮和地址展示要让不熟悉 Web3 的用户也能确认当前正在使用测试账户。

### 8.4 星宝与成长区

卡片标题：`步骤 2 · 虚拟伙伴养成`

主标题：`陪伴变成星宝的成长能量`

桌面端建议采用“星宝主视觉 + 成长指标”左右布局，活动卡位于下方。移动端先显示星宝，再显示指标和活动。

必须展示：

- 当前星宝阶段名称；
- 累计养成值；
- `首轮进度 N / 15` 或 `首轮养成已完成`；
- 100% 封顶的进度条；
- “累计养成值不因赠送而减少，也不代表孩子发育或表现等级”的提示；
- 三张活动卡。

每张活动卡包含：

- 原创扁平插画图标；
- 活动名称与一句温暖说明；
- 本次奖励 `+3 / +5 / +7 成长星`；
- 当前状态文案；
- 仅在可领取时出现的操作按钮。

### 8.5 活动卡状态矩阵

| 状态 | 按钮 | 文案/反馈 |
|---|---|---|
| 可领取 | 显示、可用 | `记录这次陪伴` |
| 冷却中 | 完全隐藏 | 使用每项拟人文案，不显示时间 |
| 当日达上限 | 完全隐藏 | `星宝今天已经很充实了` |
| 状态读取中 | 隐藏 | 骨架或 `正在读取星宝状态` |
| 状态读取失败 | 隐藏 | 友好错误 + `重试读取成长状态` |
| 等待钱包签名 | 触发项按钮保留但禁用 | `请在 MetaMask 中确认` |
| 链上确认中 | 触发项按钮保留但禁用 | `交易已提交，正在等待链上确认` |
| 成功 | 按新链上状态重新渲染 | `记录成功，获得 +N 成长星` + Etherscan 链接 |
| 用户拒签 | 按可领取状态恢复 | `已取消，本次没有记录` |
| 交易失败 | 按链上状态恢复 | 明确积分未变化，可重试 |

状态必须同时使用文字和视觉，不得只依靠颜色区分。

### 8.6 赠送成长星

卡片标题：`步骤 3 · 测试钱包赠送`

主标题：`把成长星送给另一个测试钱包`

必须展示：

- `仅限 Sepolia` 徽章；
- `可赠送成长星：N`；
- 双账本解释；
- 公开且不可撤回警告；
- 接收钱包地址输入框；
- 正整数数量输入框；
- `确认赠送成长星` 按钮；
- 等待签名、确认中、成功、拒签、链上失败、余额不足、无效地址、自己地址和零地址状态；
- 成功后的 Etherscan 交易链接。

输入框不得要求接收者姓名、备注或儿童资料。不要设计“扫码付款”“资产价值”或货币换算。

### 8.7 公开链上便签

卡片标题：`步骤 4 · 原始作业能力`

主标题：`公开链上便签（课程实验）`

该区域必须清晰可见，不折叠、不隐藏到设置页，因为它是课程最低要求。

必须展示：

- `公开内容` 徽章；
- 警告：链上内容公开，清空只改变当前显示，历史交易仍公开；
- 当前链上便签；
- 测试便签文本框；
- UTF-8 字节计数 `N / 280 字节`；
- `保存当前便签`；
- `清空当前便签`；
- 清空二次确认区，包含 `确认清空当前便签` 与 `取消`；
- 读取、签名、确认、成功、失败状态和 Etherscan 链接。

推荐占位内容：`今天完成了一次 Sepolia 测试`。不要使用包含儿童身份或健康数据的示例。

### 8.8 课程说明页脚

标题：`这份作业展示了什么？`

以四条短说明呈现：

- React + wagmi 连接 MetaMask，并把合约作为数据后端；
- Hardhat 开发、测试和部署 Solidity 合约；
- 交易哈希不等于成功，receipt 成功后才刷新；
- 累计养成值与可赠送余额分开，成长星不是 Token 或 NFT。

## 9. 视觉方向

### 9.1 关键词

温暖绘本、可信、轻松、照护感、家庭友好、适老、原创星球伙伴、轻量 Web3。

### 9.2 建议色彩

- 深海蓝绿 `#173B4D`：主文字与主要轮廓；
- 奶油纸 `#FFFAF0` / `#FFFDF7`：页面与卡片；
- 鼠尾草绿 `#3F7659` / `#DFEAD4`：安全与完成状态；
- 杏橙 `#D9773F` / `#F8DFC6`：奖励和温暖强调；
- 柔和紫 `#6F5CA8`：Web3 与焦点态；
- 危险红 `#A34338`：错误和清空操作，只小面积使用。

允许非常克制的纸张光晕或柔和渐变；不要使用加密货币常见的黑色霓虹、赛博紫、电光蓝和交易所风格。

### 9.3 字体与形状

- 中文正文优先系统无衬线；标题可用温和的中文衬线或圆体；
- 正文字号桌面端至少 18 px，辅助文字不低于 16 px；
- 圆角卡片 24–32 px，按钮圆角 14–18 px；
- 点击区域至少 48 × 48 px；
- 留白宽松，避免密集小字；
- 图标不得只用 emoji 作为最终稿，应生成统一风格的原创图标或插画。

### 9.4 星宝原创要求

星宝应是抽象的星形/蛋形宇宙伙伴，采用简单五官、柔和轮廓和不同阶段的小配件。可以借鉴“虚拟伙伴随行为成长”的机制，但不得复制支付宝蚂蚁森林、蚂蚁庄园或任何现有 IP 的角色、场景和构图。

## 10. 响应式要求

### 桌面端 1440 px

- 内容最大宽度约 1120–1200 px；
- Hero 可采用 2 列；
- 三张须知和三张活动卡各自一行三列；
- 星宝区采用主视觉与数据左右布局；
- 赠送表单可将地址、数量和按钮排成易读网格。

### 移动端 390 px

- 单列展示，严格保持信息顺序；
- 卡片左右边距至少 16 px；
- 所有主要按钮在需要时占满宽度；
- 地址自动缩略或换行，不产生水平滚动；
- 清空二次确认不遮挡内容，可使用卡片内嵌确认区；
- 320 px 宽度仍不得横向溢出。

## 11. 可访问性

- 颜色对比至少满足 WCAG AA；
- 键盘可完成连接以外的所有页面操作；
- 所有交互有清晰 `focus-visible`；
- 状态更新使用可读文字并支持 `aria-live`；
- 进度条具有名称、最小值、最大值和当前值；
- 表单错误与字段建立可感知关联；
- 禁用态不能仅靠降低透明度表达；
- 支持 `prefers-reduced-motion`，关闭星宝漂浮、呼吸和庆祝动画；
- 冷却状态对屏幕阅读器同样不泄露具体时间。

## 12. Stitch 需要生成的状态稿

至少生成以下 8 个画面或组件变体：

1. 桌面端：钱包已连接 Sepolia、三项活动都可领取的主页面；
2. 移动端：钱包未连接；
3. 桌面端：喂养与共读冷却、户外可领取；
4. 移动端：活动达到当日上限；
5. 活动交易：等待签名、确认中、成功和失败；
6. 赠送成长星：默认、字段错误、确认中和成功；
7. 便签：默认、280 字节超限和交易确认中；
8. 便签：清空二次确认。

这些是同一单页应用的状态，不要设计成八个不同产品或独立路由。

## 13. 前端接入契约

导出的视图应以 props/state 驱动，避免把示例数据写死。建议组件边界：

- `Hero`
- `SafetyNoticeGrid`
- `WalletPanel`
- `StarBuddy`
- `GrowthSummary`
- `ActivityCard`
- `TransactionStatus`
- `PointTransferPanel`
- `NotebookPanel`
- `CourseEvidenceFooter`

活动卡最少接收：

```ts
type ActivityCardState = {
  id: "meal" | "walk" | "read";
  title: string;
  reward: 3 | 5 | 7;
  available?: boolean;
  dailyLimitReached?: boolean;
  pending?: boolean;
  statusMessage?: string;
};
```

不要在生成代码中：

- 创建假的钱包连接或假交易；
- 用浏览器时间决定领取资格；
- 本地乐观增加积分；
- 编造合约地址或 API；
- 保存私钥、助记词、RPC 密钥或儿童数据；
- 把交易哈希出现直接当作成功。

现有 React + wagmi hooks 将向这些组件注入真实链上状态。只有 receipt 成功后，界面才显示成功并刷新积分。

## 14. 验收标准

- **UI-01** 桌面端与移动端都保留完整 4 步主流程。
- **UI-02** 首屏能看见 Sepolia、概念验证和“无价格、不可兑换”。
- **UI-03** 用户能同时理解累计养成值与可赠送余额。
- **UI-04** 三张活动卡准确显示 3、5、7 奖励。
