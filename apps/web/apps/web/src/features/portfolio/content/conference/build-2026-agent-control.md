# Observe and control agents across any framework with open source tools

> [!summary] 一句话
> Agent 安全不能只靠系统提示词：先把业务政策变成可执行评测，用自动生成的单轮和多轮场景找出失败，再通过 Agent Control Specification（Agent 控制规范）在输入、模型、状态、工具和输出五个检查点实施确定性控制，最后用持续评测和自适应攻击者追踪生产中的新风险。

## 为什么 Prompt 约束不够

普通聊天模型主要产生文本，Agent 则会调用工具、读取数据、修改文件和影响外部系统。风险不再只发生在最终回答，而可能发生在整个执行链条中：

1. 模型可能误解任务，在推理早期就选择了错误目标。
2. 输入、检索结果或工具返回可能含有恶意指令和不可靠信息。
3. Agent 可能选择正确工具，却使用了错误参数、错误身份或过大的权限。
4. 多个看似安全的局部动作，组合后可能形成未预料的系统行为。

因此，安全不能只写在一个 System Prompt（系统提示词）里。团队需要两种互补机制：**Evaluation（评测）负责发现行为是否符合要求，Control（控制）负责在运行时阻止不能发生的动作。**

## 四类 Agent 失败

### 1. Instruction failure（指令失败）

Agent 没有正确遵守任务、角色或业务政策。它可能遗漏必要步骤、被新输入带偏，或在长对话中逐渐遗忘最初约束。此类问题不能只测试“最终回答像不像”，还要检查规划、工具选择和多轮一致性。

### 2. Information integrity failure（信息完整性失败）

Agent 使用了错误、过期、被污染或带有 Prompt Injection（提示注入）的信息。检索结果和工具输出不应天然被视为可信指令；系统需要区分数据与指令，并验证关键事实的来源和权限。

### 3. Tool misuse（工具误用）

Agent 调用了不该使用的工具，或以不安全方式调用了正确工具。例如越权读取、把敏感数据发给外部服务、对不可逆操作缺少确认、在错误作用域执行批量动作。工具调用是 Agent 与真实世界连接的边界，也是最需要确定性控制的地方。

### 4. Emergent behavior（涌现行为）

单个步骤都没有明显违规，但长任务、多 Agent 协作或环境反馈叠加后出现了设计者没有预期的策略。它要求测试多轮、多步骤和系统级结果，而不能只测试孤立样例。

## 从文字政策到可执行评测

演讲的第一条主线是把“应当安全、可靠、合规”这类抽象要求转换成机器可以重复执行的测试流程：

```text
业务政策与角色定义
        ↓
识别风险、允许行为和禁止行为
        ↓
生成单轮与多轮测试场景
        ↓
Rubric Judge 按场景化标准评分
        ↓
定位失败证据并形成回归测试
```

风险和角色可以用 YAML 等配置格式表达，使政策能够被版本控制、审查和复用。重点不是把自然语言换成配置文件，而是要求团队明确回答：谁在什么上下文中，可以访问什么数据、调用什么工具、产生什么影响，以及何时必须交给人确认。

## ASSERT：策略驱动的 Agent 评测

ASSERT 是 Microsoft 在 Build 2026 推出的开源策略驱动评测框架。它试图解决传统测试集覆盖不足的问题：

1. 从 Agent 的角色、任务和组织政策中提取要验证的要求。
2. 把要求转成具体、可测量的评价标准，而不是模糊的“表现良好”。
3. 自动生成针对性场景，包括一次交互即可暴露的问题和需要多轮诱导才能出现的问题。
4. 运行被测 Agent，收集回答、状态变化和工具行为。
5. 使用 Judge（评判模型）按 Rubric（评分规程）判断是否违反要求，并保存失败证据。
6. 把已发现的失败加入回归集，避免下一次修改重新引入同类问题。

ASSERT 的价值在于让安全评测接近软件测试：政策变化时可以重新生成或调整场景，Agent、模型、工具或 Prompt 更新后可以自动回归。它支持多种 Agent 框架，避免安全测试被绑定到某一家 SDK。

## Rubric：根据实际上下文评判“好不好”

静态 Benchmark（基准测试）只能覆盖预先定义的通用能力，而企业 Agent 的合格标准通常取决于具体角色。例如，同一段客户信息对客服 Agent 可能可见，对营销 Agent 则可能不可见。

Rubric evaluator（评分规程评测器）会根据 Agent 定义和使用场景生成专属评价维度，并为不同维度设置权重。它可以把“回答正确”拆成任务完成、政策遵从、信息依据、工具使用、安全性等多个分数，再汇总为场景化结果。

这类 Judge 仍然是概率模型，不能替代所有确定性验证。适合用它判断语义和复杂行为；权限、数据格式、金额上限、允许工具列表等明确规则，仍应由代码或策略引擎直接执行。

## Agent Control Specification：在五个检查点实施控制

评测告诉团队哪里会失败，但生产系统还需要在失败发生时进行阻断。ACS（Agent Control Specification，Agent 控制规范）用可移植、可审计的策略契约描述控制要求，并把控制放在 Agent 生命周期的五个位置：

| 检查点 | 需要控制什么 | 示例 |
| --- | --- | --- |
| Input（输入） | 用户请求、文件和外部事件能否进入 Agent | 检测敏感信息、恶意指令、越权任务 |
| LLM（模型） | 哪个模型可以处理哪些数据和任务 | 限制模型、地区、数据分类或推理配置 |
| State（状态） | 记忆、会话和中间结果能否读取或写入 | 隔离租户、限制长期记忆、设置保留周期 |
| Tool execution（工具执行） | 工具、参数、身份和作用域是否合法 | 阻止危险命令、限制金额、要求人工审批 |
| Output（输出） | 结果能否返回、保存或发送到外部 | 防止数据泄露、检查政策与格式 |

ACS 位于 Agent Runtime（智能体运行时）与 Policy Engine（策略引擎）之间。Agent 可以用 Microsoft Agent Framework、LangChain、CrewAI 或自定义框架实现，但控制契约不需要随框架重写。YAML 等可版本化格式也使安全团队能审查“规则发生了什么变化”，而不是在多个 Prompt、网关和业务函数里追踪散落逻辑。

## 为什么评测和控制必须分开

- **只做评测**：可以发现问题，但生产中的危险动作仍可能在报告生成前已经发生。
- **只做控制**：可以阻断已知规则，却不知道 Agent 是否正在以新的方式退化，也难以验证控制是否覆盖真实风险。
- **二者结合**：评测发现失败模式并形成证据，控制把明确边界落实到运行时；生产数据再反过来扩充评测集。

这也是“可观察”与“可控制”的区别。Tracing（链路追踪）让团队看到 Agent 做了什么；Evaluation 判断做得好不好；Control 决定哪些事情绝对不能发生。

## 持续评测与自适应攻击者

一次上线前红队测试无法覆盖持续变化的系统。模型会更新，工具和数据源会变化，用户会发现新的交互方式，攻击者也会调整策略。演讲提出把评测变成长期生产环：

1. 从真实流量和 Trace 中抽取新的行为模式与失败信号。
2. 使用自动攻击者生成 Prompt Injection、数据泄露、工具误用和目标冲突场景。
3. 运行测试并寻找当前 Agent 最薄弱的位置。
4. 将新失败加入回归集，推动 Prompt、工具、检索、策略或模型调整。
5. 对修复版本重复评测，确认没有引入新的安全回归。

前瞻方向是使用 Reinforcement Learning（强化学习）驱动的攻击者，不断根据被测 Agent 的反应调整下一轮攻击。这比固定攻击提示更接近真实对手，但也必须设置预算、隔离和停止条件，防止测试系统本身造成资源或数据风险。

## Human in the Loop 应放在哪里

人在回路不应意味着“每一步都弹窗”，否则用户会形成批准疲劳。更合理的分层是：

- 读取公开信息、生成草稿等低风险动作可自动执行并保留日志。
- 访问敏感数据、改变权限或向外部发送信息时，根据身份和作用域执行策略检查。
- 删除、付款、发布、签约等高影响或不可逆动作，要求明确的人类确认。
- 当 Agent 行为偏离任务、评测置信度不足或控制规则冲突时，暂停并把上下文交给人处理。

人工确认必须出现在动作执行之前，并清楚展示目标、范围和影响；只有一个“是否允许”按钮而没有可理解的上下文，不构成有效监督。

## 与企业安全体系的衔接

这套方法不是另建一套孤立的“AI 安全部门”，而要接入既有身份、数据和监控体系：

- 使用独立 Agent 身份和最小权限区分人、Agent 与服务账号。
- 通过 Trace 记录模型调用、状态变化、工具执行和 Agent 间交接。
- 将数据分类与 DLP（Data Loss Prevention，数据丢失防护）策略用于输入、工具和输出。
- 把评测失败、安全事件和策略阻断接入统一告警与审计流程。
- 用生产失败样本更新开发阶段测试，而不是只留在运营工单里。

Microsoft 的相关 Build 资料把 Purview 数据保护、Foundry Observability、ASSERT、ACS、Rubric 与 Agent Optimizer 放在同一条 DevOps 闭环中。产品可以替换，但“政策—测试—控制—观察—改进”的结构具有通用性。

## 对实际项目的落地清单

### 开发前

- 写清 Agent 角色、数据边界、可用工具和禁止行为。
- 把高风险动作分级，指定哪些必须人工批准。
- 为状态和长期记忆定义租户隔离、保留周期和删除规则。

### 上线前

- 同时准备正常任务、边界条件、对抗输入和多轮诱导测试。
- 对工具调用验证名称、参数、身份、作用域和副作用。
- 将每个已知事故转成可重复回归用例。
- 验证控制规则在输入、模型、状态、工具和输出五个检查点真实生效。

### 生产中

- 记录完整 Trace，并将评测结果关联回产生它的具体执行链。
- 监控任务完成率、拒绝率、人工接管率、策略阻断和工具失败。
- 对模型、Prompt、工具、权限或数据源变化重新运行回归。
- 定期用新场景进行红队测试，不把某次 Gate 通过视为永久安全。

## 容易踩的坑

1. **把合规文档当控制措施**：政策只有变成测试和运行时规则才会真实影响 Agent。
2. **只评最终答案**：危险可能已经在工具调用或状态写入阶段发生。
3. **只测单轮问题**：很多越权和目标漂移需要多轮交互才会暴露。
4. **全部依赖 Judge 模型**：可确定的规则应由代码或策略引擎执行，避免概率判断替代硬边界。
5. **控制逻辑绑死某个框架**：换 Agent SDK 时容易漏掉安全能力，应尽量采用独立、可移植的控制契约。
6. **持续评测没有反馈闭环**：生成大量分数却不进入修复、回归和发布决策，只会增加仪表盘而不会提高可靠性。

## 大白话

评测像考试，负责发现 Agent 会不会犯错；ACS 像门禁，负责在真实工作时挡住不能做的事；Trace 像监控录像，负责还原它做过什么；持续红队则像不断更新题库的安全演练。

只考试不设门禁，Agent 即使考试不及格也可能继续操作真实系统；只设门禁不考试，团队只知道挡住了旧问题，不知道新问题从哪里冒出来。完整做法是让题库、门禁、录像和修复流程互相连接。

## 前瞻方向

- 安全评测将从固定数据集转向根据角色、生产上下文和历史失败动态生成。
- 攻击者模型会通过强化学习寻找新的薄弱点，红队从阶段性项目变为持续服务。
- 控制规则会从散落在 Prompt 和代码中的实现，转向跨框架、可版本化的开放规范。
- Agent 的评测对象将扩展到整个执行轨迹：规划、状态、工具、交接和最终结果。
- 安全团队与开发团队的协作会更接近 Policy as Code（策略即代码）和安全回归测试。
